We found three broken integrations in one afternoon because we were trying to record a demo.

Embarrassing, but useful. We had health checks and logs, and the scheduled jobs kept running. What we did not have was evidence that a request could still travel through the system and come back with an answer.

I build AI agents that help run business operations. A lot of that work happens between systems: a comment arrives, the assistant reads the context, something gets drafted or answered. When those connections stop working, there may be nothing visibly wrong. A person asks a question, gets no answer, and carries on without the assistant.

Our dashboard stayed green through all of it.

## The webhook arrived. Nothing happened.

The first failure was in our shared inbox tool. People could mention the assistant in a comment and expect a response.

The tool started sending comment events under a new event name. Our handler only matched the old names. The requests still reached us. We received them, wrote a line to the log, and then ignored them because they did not match a branch we handled.

A mention could pass through all of that and get no response.

There was no exception. Nothing timed out. The webhook endpoint had done exactly what its code said to do. Unfortunately, that code treated an event it did not recognize as something uninteresting.

A log line saying that an event arrived looked like evidence the integration worked. It only proved that the first part worked. We were not checking whether the event became an assistant request, or whether that request produced a reply.

We added a handler for the new event. Without other changes, the next renamed event could break it again.

We needed tests for both payload shapes, using representative examples of the old and new events. Each test had to reach the same outcome: a comment mentioning the assistant becomes work for the assistant. A test that only checks whether the endpoint accepts the payload would have passed throughout the failure.

We also needed to distinguish deliberately ignored events from events we had never seen before. Ignoring a known event type can be correct. Silently ignoring a new comment event deserves attention.

## Two more ways to do nothing

The next failure was in the background worker that diagnoses errors. Its production model API key had become invalid.

Every item it tried to process failed with "401 unauthorized", the API's way of saying the key is no good. Meanwhile, the health endpoint kept saying ok.

The worker could wake up and attempt work. It just could not do its job. Our health check never reached the dependency that made that task possible.

The worker meant to explain errors was itself broken. Awkward. We needed to see its failure somewhere outside its own diagnosis path.

Then we looked at Slack.

The bot account used by the sync had been deactivated. The sync job kept reporting “idle, 0 new messages” on its regular schedule.

That message sounds ordinary. A quiet channel can have no new messages. But a deactivated account cannot establish whether a channel is quiet. We had allowed “could not read” to look like “read successfully and found nothing.”

These were separate failures. One dropped events, one failed during processing, and one reported an empty result without working access. All three disappeared behind status messages that sounded reassuring.

## What a healthy job has to prove

I still want a cheap check that tells me whether a process is alive. It helps with restarts and routing. I just do not want that check to stand in for whether an integration works.

For that, I want to know when it last completed useful work. Could it authenticate? Could it read the source? Did an accepted request finish? Did the reply reach its destination?

Those answers need separate states. A successful read with no new messages is idle. A failed read is an error. An authentication failure should mark the job as failed and alert someone who can fix the credentials or account. It should never become an empty result.

We also needed to investigate suspicious zeroes.

Suppose a supplier inbox usually produces assistant requests during the working week. Then it produces none. That does not prove something is broken. The team might be away, or the workflow might have changed. But it is enough to ask whether the source is still connected.

The useful comparison is with that job’s own history and expected schedule. A quiet weekend should not wake someone up. An active workflow going silent should not stay invisible for months.

I would also put the last successful completion beside the current status. “Running” tells me what the process is doing now. “Last reply delivered months ago” tells me something much more relevant about the integration.

## Send something through the whole path

Watching real traffic still leaves a gap. Sometimes there genuinely is no work. We need a way to test the path without waiting for a person to discover it is broken.

An end-to-end canary can do that.

A scheduler posts a synthetic message in a designated test location. The message mentions the assistant and asks for a harmless, recognizable response. It enters through the same integration as an ordinary request. The assistant processes it and posts a reply. A separate checker waits for that reply and alerts if it does not arrive within the expected window.

The checker needs to look at the destination. An internal “reply sent” log is not enough. Give each synthetic request an identifier so an old reply cannot satisfy a new check.

The message should exercise a small, safe task. For example, ask the assistant to acknowledge a test supplier reference. It should not contact a supplier or change an operational record.

That path also needs loop guards. The assistant must recognize its own account and ignore its own replies. Otherwise, the reply can arrive as another comment event and start another run. Tests should cover both incoming payload shapes and the assistant’s outgoing messages returning through the webhook.

The checker itself needs watching too: if a scheduled check does not run, that should also raise an alert. And the alert path needs to be independent. If we are checking Slack access, relying only on that same Slack integration to report failure defeats the check.

## The demo was an accidental audit

A demo makes you follow the whole sequence. Start where a person starts. Make a request. Wait for the result. Look at the place where the result should appear.

That afternoon, we finally did that across paths we had assumed were working.

I am glad we found the failures. I am less pleased that preparing a recording was what made us look. The dashboard had answered the questions we built into it, and those questions were too small.

I still think a demo is a great audit. Pick a real workflow and follow it all the way through. But the scheduled checks should do that work between demos. I want the next missing answer to reach us as an alert, while the person who asked is still waiting.
