The agent that needs you most may be the one producing no output.

Picture a back office run by six AI agents. One checks October invoices against orders. One sorts the morning inbox. One drafts a reply to a refund request. And one has stopped, because it found two different bank accounts for the same supplier and does not know which one to use.

From a distance, all six look busy. Only one needs you, and it is the quiet one.

I want a console that brings that decision to me. Otherwise I spend the time I saved by delegating on hunting for the next decision.

## Coding already has good answers

[Ed Engelking II's write-up of Podium](https://edengelking.com/blog/podium-a-control-room-for-claude-code/) was the first thing that made this problem concrete for me: one view for many Claude Code sessions and their child agents.

Since then, two tools made the idea mainstream.

In May 2026 Anthropic shipped [Agent View in Claude Code](https://claude.com/blog/agent-view-in-claude-code) as a research preview. You open it with the left arrow or `claude agents`. Each row shows a session, whether it needs your input, its last response, and when you last touched it. You can peek at the last turn and answer inline, and the session picks back up. It is exactly the core idea: the decision comes to you, not the other way around.

<Figure src="/writing/the-agent-is-waiting-for-you/agent-view.png" width={1408} height={556} alt="A terminal list of Claude Code sessions grouped into Needs input, Working and Completed. Each row shows a session name, its last message, and the time since the last interaction." caption="Agent View in Claude Code. Screenshot from Anthropic's announcement, claude.com." />

[Orca](https://www.onorca.dev/) goes wider. It is a free, open-source app for running Claude Code, Codex and other coding agents in parallel, each in its own git worktree, with terminals, diffs and a browser in one window. It also shows usage for Claude and Codex, and there is a mobile app to watch agents from your phone.

<Figure src="/writing/the-agent-is-waiting-for-you/orca.png" width={1488} height={812} alt="The Orca app: a sidebar of projects and branches, one task running three agents on different runtimes, split terminal panes with Claude Code and Codex, and a status bar with usage for both." caption="Orca, an open-source workspace for coding agents. Screenshot from onorca.dev." />

If you write code with agents, start with these. For Claude-only work, Agent View is already in the tool you use. For a mix of coding agents, Orca is the more complete option today.

## Business agents need a different first screen

My work is mostly the other side: agents that move business data. Invoices, suppliers, refunds, bookings. Here the questions are about money and records, and the people answering them are often not engineers.

That changes what the first screen should do. So I built a prototype for it, called Heedroom.

<Figure src="/writing/the-agent-is-waiting-for-you/console.gif" alt="An animated agent workspace. A sidebar groups six back-office agents by team, an inbox shows one blocked question about two bank accounts for a supplier, the operator opens it, picks the contract account, and the onboarding agent resumes." caption="Heedroom, an interactive prototype with synthetic data. Not a screenshot of a production system." width={1492} height={812} />

You can [click through the live prototype](https://project-agent-console-demo-745.magicpatterns.app): open any agent, switch tabs, and make the decision yourself.

Four things are different from the coding tools.

**The decision carries its own context.** The supplier question does not just say "needs input". It says what it blocks, which sources disagree (the signed contract says the account ends in 7001, yesterday's email says 7044), and what happens after you answer. Paying the wrong account is money out the door, so the agent never picks between conflicting sources on its own. You decide from the card.

**Agents are grouped by business area, not by repository.** Finance, Operations, Inbox and admin. A finance lead looks at their team, not at branch names.

**Every agent shows where it runs.** Real setups are mixed: the invoice matcher on Claude, inbox triage on a small cheap model, the refund writer in Codex. When something goes wrong, "which agent" is not enough. You want the runtime and the model, because that tells you whether you have a model limit or a data problem, and why one agent costs more than the others. Costs are shown per runtime and always labelled as estimates.

**Silence is a state, not a success.** An agent that stops reporting has not necessarily finished. It may be waiting, working quietly, or gone. Every status needs a last-seen time and a point after which it counts as stale. A green "running" badge would hide that gap.

The gap is not inferred to be successful completion." caption="A proposed state-reconciliation rule. Time spacing is schematic." />

## Put blocked decisions first

In Heedroom the inbox is the home screen, and the agents live in the sidebar. The order matters.

Next to the supplier question sit two very different things: a refund reply that is drafted and ready to read, and an agent that went quiet twelve minutes ago. One needs a choice, one needs a read when there is time, one needs an honest warning. If all three get the same amber badge, I am the one doing the sorting.

<Figure src="/writing/the-agent-is-waiting-for-you/inbox.svg" alt="A proposed decision inbox separates an unresolved question that blocks work, an item ready for review, and a disconnected reporter whose current state is unknown. The examples are synthetic." caption="Original interface sketch with synthetic items. This is a proposal, not a screenshot of a working console." />

Age alone should not set priority. A decision that blocks supplier onboarding, and every payment after it, matters more than an older optional report. The console should show why it put an item first and let me change the order.

## Tie every check to the data it saw

A list of agents shows who is working. It cannot show that their results still fit together.

Say the invoice agent matched invoice 2214 against order 118 at ten o'clock. At eleven, someone edits the order. The earlier match is now about a version of the order that no longer exists. A good console ties each check to the data it actually saw and flags the results that a later change made stale.

That is also why I would not rank agents by tokens used or tasks finished. Both go up when work is being redone. I would measure time spent waiting for decisions, repeated interruptions, stale results caught, and time to an accepted result.

## Which one would I use

Only Claude Code, only code: Agent View. It is built in and does the core job.

Several coding agents across Claude Code, Codex and others: Orca, or extend [Podium](https://github.com/eengelking/podium) if you want something you shape yourself.

Agents doing business operations, with people who decide about money and records: that is the gap Heedroom is for. It is still a prototype, and I am testing it against one question.

When I come back to the desk, do I find the right decision sooner? If I still have to open every agent to work out who needs me, the console has not done its job.
