The agent that needs you most may be the one producing no output.

Picture a back office run by six AI agents. One is checking October invoices against orders. One is sorting the morning inbox. One is drafting a reply to a refund request. And one has stopped, because it found two different bank accounts for the same supplier and does not know which to use.

From a distance, all six look busy. Only one needs you, and it is the quiet one.

I want an agent console to bring that decision to me. Otherwise I spend the time I saved by delegating on searching for the next decision.

[Ed Engelking II's write-up of Podium](https://edengelking.com/blog/podium-a-control-room-for-claude-code/) made this problem concrete for me. His console brings Claude Code sessions and their child agents into one view. His sessions write code; mine would mostly move business data. The design question is the same: what should the first screen ask me to notice?

## Put blocked decisions first

A grid of agent cards gives a useful overview. I would still put a decision inbox above it.

Take the supplier case. The signed contract says the account ends in 7001. Yesterday's email from their accountant says 7044. The onboarding agent should not pick one. A wrong value here is money out the door, so the agent stops and asks.

Next to it in the inbox sit two very different things: a refund reply that is drafted and ready for review, and an agent that stopped reporting twelve minutes ago. One needs a choice, one needs a read when there is time, one needs an honest warning. If all three get the same amber badge, I am the one doing the sorting.

<Figure src="/writing/the-agent-is-waiting-for-you/inbox.svg" alt="A proposed decision inbox separates an unresolved question that blocks work, an item ready for review, and a disconnected reporter whose current state is unknown. The examples are synthetic." caption="Original interface sketch with synthetic items. This is a proposal, not a screenshot of a working console." />

The question card should carry its own context: what it blocks, which sources disagree, and what happens after I answer. I should be able to decide from the card, without opening the agent's full history to reconstruct the task.

Age alone should not set priority. A decision that blocks supplier onboarding and every payment after it matters more than an older optional report. The console should show why it put an item first and let me change the order.

## Show where each agent runs

Real setups are mixed. The invoice matcher might run on Claude through Claude Code, the email triage on a small, cheap model, and a coding helper in Codex on an OpenAI model. When something goes wrong, "which agent" is not enough. I want to know which runtime and which model.

So every card in my console names both, for example "Claude Code · Sonnet" or "Codex · GPT". It sounds like a detail. It answers real questions fast: is this a model limit or a data problem, why did this agent cost more than the others, and which tool do I open to look closer?

It also keeps comparisons honest. Two agents doing similar work on different models are not the same experiment, and the screen should not pretend they are.

## Keep unknown states visible

An agent that stops reporting has not necessarily finished. A quiet agent may be waiting, working without new events, or gone.

Every status needs a last-seen time and a point after which it counts as stale. If the reporter disappears halfway through the invoice run, the screen should say the result is unknown. A green "running" badge would hide the gap.

The same honesty applies to cost. If one runtime reports exact usage and another only gives token counts, label the second one an estimate. Adding unlike numbers into one precise-looking total makes the whole screen harder to trust.

## Tie every check to the data it saw

A list of agents shows who is working. It cannot show that their results still fit together.

Say the invoice agent matched invoice 2214 against order 118 at ten o'clock. At eleven, someone edits the order. The earlier match is now about a version of the order that no longer exists. A good console ties each check to the data it actually saw and flags the results that a later change made stale.

That is also why I would not rank agents by tokens used or tasks finished. Both go up when work is being redone. I would measure time spent waiting for decisions, repeated interruptions, stale results caught, and time to an accepted result.

## Test whether a small console saves attention

My first version would be small: a few agents, one place, no remote approval button. Its only job is to show the next decision and enough context to make it.

If the agents are coding sessions, I would compare that with [Podium's existing implementation](https://github.com/eengelking/podium) before building anything, and check what Claude Code's [mods](https://code.claude.com/docs/en/plugins/mods/overview) can observe in the runtime version in use. Extending a tool that exists may solve the problem without another dashboard.

The test is simple. When I come back to the desk, do I find the right decision sooner? If I still have to open every agent to work out who needs me, the console has not done its job.
