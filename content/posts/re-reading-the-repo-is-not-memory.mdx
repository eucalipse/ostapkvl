A Rust tool called Graphicle gives coding agents a persistent graph of the codebase instead of having them re-read files on every call. Its published benchmarks claim large drops in latency and memory use between two recent versions on a real, large repository. I have not run it myself, so take the numbers as the project's own claim, not an independent measurement.

<Figure src="/writing/re-reading-the-repo-is-not-memory/source-screenshot.jpg" alt="The GitHub README of the Graphicle repository, describing it as a code graph and memory tool for coding agents that maps a repository and remembers its docs, decisions and past agent sessions." caption="Graphicle-AI/graphicle on GitHub. Not my project; shown for reference." width={1456} height={840} />

What the tool is actually for interests me more than the benchmark. A coding agent without a code graph re-derives the same structure, the same file relationships, the same "where is X defined," every time it is asked. That is not caution. It is the absence of anywhere to keep the answer from last time.

Worth being precise about scale here: Graphicle is a small project, a few hundred stars on GitHub. A separate, much larger project with a similar name and a similar pitch, Graphify, has tens of thousands of stars and backing from a startup accelerator. They are not the same tool, and I want to be clear I am not inflating Graphicle's size by association. What's interesting is that four genuinely different tools converged on overlapping answers to the same problem, at very different scales.

## Four answers to "what should the agent not have to re-derive"

**Graphicle** builds a persistent graph of the repository — files, symbols, their relationships — so a coding agent can query structure instead of re-reading it. Small project, Apache-2.0, works with Claude Code, Cursor, Codex and other MCP clients.

**Graphify**, the larger project in the same space, makes the sharpest version of the argument for this approach: a vector search retrieves code that looks similar to a query; a graph retrieves code that is actually connected to it. The two are often different files. The most structurally relevant piece of code — the one function that will break if you change this one — can be the least textually similar to whatever you searched for. That's a real limitation of embeddings-only retrieval, not just a marketing line, though the specific cost-savings numbers attached to it are the vendor's own and I have not checked them.

Not my project; shown for reference." width={1492} height={812} />

**Aider's repo-map** takes a lighter version of the same idea: parse the repo with tree-sitter into a graph of files and symbol references, then rank it to surface the files most relevant to the current edit. No persistent database, no server — it rebuilds the map each run, but still answers "what's connected" rather than "what looks similar."

<Figure src="/writing/re-reading-the-repo-is-not-memory/aider-repomap-screenshot.jpg" alt="The aider.chat blog post titled Building a better repository map with tree sitter, describing the difficulty of making complex changes in a large pre-existing codebase without first understanding how the code relates." caption="aider.chat's own write-up of the repo-map approach, from 2023. Not my project; shown for reference." width={1492} height={812} />

**Continue.dev** goes the other way and stays with embeddings only, no graph. That's the useful contrast: if your questions are lookups against documentation or loosely related code, embeddings are a fine tool, cheaper to build and reason about. The graph earns its cost specifically when the question is about structural connection, not textual similarity.

## The same question, asked about a different kind of memory

I built a shared memory space for a different purpose — people and AI systems leaving short texts that connect by meaning — and landed on a rule that generalizes further than I expected when I wrote it: keep identity, permission and time as plain data, and let embeddings only suggest what might be related. Similarity is not truth, and it should never override who is allowed to see what. That's the center of [Building a memory garden with pgvector](/writing/memory-garden-pgvector).

A code graph and a conversational memory store look nothing alike on the surface. But both are answering the same design question: what is worth keeping so the next call doesn't have to re-derive it, and what has to stay re-checked every time because keeping a stale answer is worse than redoing the work? For code, that line falls differently than for a person's stated preference — a file's structure changes less often than a person's mind — but the line still has to be drawn somewhere, on purpose, rather than defaulting to "remember everything" or "remember nothing."

## What I'm taking from it

Not a benchmark to chase, and not a single winning tool. The reusable piece is the question itself: before adding any persistent store to an agent, ask what specifically becomes safe to stop re-deriving, and what still needs a fresh check every time because the cost of a stale answer is higher than the cost of redoing the work. Four tools answered that question differently — full graph, lightweight graph, embeddings only — because the right answer depends on whether your retrieval problem is mostly about structural connection or mostly about topical similarity. Knowing which one you actually have matters more than picking a tool before asking it.
